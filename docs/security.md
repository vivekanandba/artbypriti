# Security posture

What this site does about security, what it deliberately does not, and what it **cannot**. Written
because `CON-SEC-004` asks for the headers a deployed project sends to be *stated* — and because the
honest half of that statement here is the part about what GitHub Pages makes impossible.

Rules cited: `CON-SEC-002` (scanning as a CI gate), `CON-SEC-003` (shipped vs build tree),
`CON-SEC-004` (declare the headers or record why not), `CON-SEC-005` (a security pass is part of
done).

## The shape of this target

A static Hugo site on GitHub Pages. **No server, no database, no authentication, no user input, no
API.** Most of the classic web attack surface simply is not present — there is nothing to inject
into and no session to steal. What remains is supply chain, secrets in history, and what the
browser is told it may load.

## Headers (CON-SEC-004)

| Header | Status |
| --- | --- |
| `Content-Security-Policy` | **Sent**, via `<meta http-equiv>` in `layouts/partials/head-custom.html` |
| `Referrer-Policy` | **Sent**, via `<meta name="referrer">` — `strict-origin-when-cross-origin` |
| `X-Content-Type-Options` | **Cannot be sent.** Ignored in a meta tag; needs a real header |
| `X-Frame-Options` / `frame-ancestors` | **Cannot be enforced.** `frame-ancestors` is ignored in a meta tag by specification |
| `Strict-Transport-Security` | Not ours to set — GitHub Pages sends it for `*.github.io`; the custom domain relies on GitHub's TLS |

**GitHub Pages cannot set HTTP headers at all.** That is a property of the host, not an oversight,
so the limitation is recorded here rather than left implicit. The practical consequence: this site
**cannot defend against clickjacking** or MIME-type sniffing. For a public gallery with no login and
no user data, that is an accepted and low-consequence gap. It would not be acceptable if the site
ever grew a form, a login, or anything a visitor could be tricked into clicking.

### The CSP, and why it is not stricter

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
img-src 'self'; font-src 'self'; connect-src 'self';
object-src 'none'; base-uri 'self'; form-action 'none'
```

Measured against the **built output**, not assumed from templates:

- **0 inline `<script>` blocks** → `script-src 'self'` is strict, which is the directive that
  matters most.
- **0 inline `<style>` blocks**, but **184 `style=` attributes** on the home page alone, emitted by
  the theme's `album-card.html`. Attributes cannot be hashed practically, so `style-src` needs
  `'unsafe-inline'`. **This is the one weak directive**, and the fix is known: move those attributes
  into `assets/css/custom.css`. That changes rendering, so it is its own change with its own visual
  review — not something to smuggle into a security commit.
- **No external origins and no `data:` URIs**, so everything else is `'self'`.

Verified in a real browser that the policy breaks nothing: zero CSP violations across the home,
artwork, about and category pages, compared against a build without the policy.

## Scanning (CON-SEC-002, CON-SEC-003)

| Gate | Runs | Threshold |
| --- | --- | --- |
| `gitleaks` over **full git history** | every PR | any finding fails |
| `pip-audit` on `requirements-dev.txt` | every PR | `--strict` |
| `npm audit` on devDependencies | every PR | `--audit-level=high` |
| `scripts/check-shipped-deps.py` | every PR | any external origin fails |

**Shipped versus build (CON-SEC-003).** The published site has **no runtime dependencies** — every
byte is generated by Hugo or vendored into the repo. So everything scannable is build-only
(Playwright, pytest), which per the rule is the *more* dangerous half, because it executes in CI
with credentials. `check-shipped-deps.py` exists to keep the clean half clean: the day a CDN script
or remote webfont appears, the shipped tree acquires a supply chain and the build fails saying so.

**Cadence.** Deterministic checks run per PR. CVE feeds move on their own schedule, so a
vulnerability published today must not fail an unrelated pull request — that is how gates get
bypassed wholesale (`CON-PROC-003`).

## What the secret scan does *not* cover

Stated plainly, because a green badge that implies more than it checks is worse than no badge
(`CON-VER-005`).

`gitleaks` reports **no leaks** across this repository's full history, and it genuinely detects real
secrets — verified by planting a GitHub PAT, a Slack token and an RSA private key, all three caught.

But it does **not** cover the exposure in [incident #10](incidents.md): the public `.wpress`
WordPress backup containing a database dump with one password hash and ~1,250 email addresses.
Two reasons, both structural:

1. The archive is **binary**, which gitleaks does not meaningfully scan.
2. gitleaks detects **credentials** — API keys, tokens, private keys. It has **no rules** for
   password hashes or personal data, which is what that dump actually contains.

So no allowlist was added: there is nothing being suppressed, and adding one would have silently
blinded these paths to future *real* findings. The incident #10 risk is **accepted and uncovered by
this control** — it is managed by the decision recorded in the ledger, not by the scanner.

## Known gaps

- Clickjacking and MIME-sniffing protection are **unachievable** on this host (above).
- `style-src` requires `'unsafe-inline'` until the theme's inline style attributes move to CSS.
- Incident #10 remains an accepted risk; the admin password should be rotated if reused anywhere.
- Dependency *license* compliance is not checked. Out of scope.
